## 一张订单的一生

先别急着聊那些高深的技术词，咱们先跟一张普通的网购订单走一趟。

你捧着手机点下“提交订单”的那一瞬间，后台服务器得在一眨眼的几十毫秒里，连珠炮一样干完一串事：查库存、算满减、过风控，最后落库生成订单。

干完这一串，它就停下了，开始漫长的“等”。

先等买家掏钱，倒计时 30 分钟，不付就自动取消关单。付了钱，通知仓库备货，接着等仓库发货。发了货，等物流配送和买家签收。好不容易签收了，系统还得再掰着指头等满七天——等过了无理由退换期，才敢把货款结算给商家。

你看，一张小小的订单，从生到死少说也要折腾大半个月。真正忙着算逻辑的就那么几秒钟，剩下绝大部分时间，全在“等”：等人掏钱、等外部系统回传、等时间一点点走完。

## 刚开始写代码，大家都是这么过来的

第一版代码没人会想太复杂，需求刚下来时，谁都是两分钟搞定。

下单那一连串校验，写进一个 `createOrder` 方法，掏出 if-else 一路判断下去。至于后面那几次漫长的“等”，业内也有最经典的土办法：订单表里加一个 `status` 状态字段，再在后台起几个定时任务，每隔一分钟扫一遍表。

发现超过 30 分钟还没付款的，把 `status` 改成“已取消”，顺手把锁定的库存退回去；看到签收满七天的，触发结算，把钱打给商家。

能跑，而且刚上线时跑得挺顺畅。

转折发生在业务跑起来之后。产品经理和运营的新需求接踵而至：搞预售，买家得先付定金、过三天再付尾款；做跨境电商，发货前得多插一步海关申报；大促期间风控吃紧，大额订单必须卡住等人工复核；接着又是部分退款、换货、拆单分开发货……

每次接需求，大家都会顺手补刀：不就是 `status` 多加一个枚举值嘛，定时任务多写一个，代码里再多套两层 if-else。

就这么修修补补过了一年，当初清爽的单子彻底成了一团乱麻。`status` 字段不知不觉膨胀到了十几种状态，七八个定时任务散落在好几个不同的服务里，时不时还会暗中互相踩脚。某天客服火急火燎跑来敲桌子：“这张订单卡了两天没动静，到底卡在哪一步了？”

你点开数据库，又去翻日志，再顺着三四个微服务的代码顺藤摸瓜，折腾了一整个下午，才勉强把事情的原委拼凑出来。

## 真正的病根在哪？

静下心来琢磨琢磨，这锅真不能扣在 if-else 头上。计算机底层本来就是靠条件分支运转的。真正把系统拖垮的，是两个藏在暗处的硬伤：

**第一，流程是隐形的。** 先做什么、后做什么、什么情况该走哪条岔路，系统里没有任何一张图或者一个地方写得明明白白。整套流程全被打碎成渣，混在代码逻辑的角角落落里，除了写代码那一刻的你，谁也理不清全貌。

**第二，等待靠手工硬缝。** 订单停下来等谁、走到哪一步了、什么时候该被叫醒，全靠开发人员人肉用状态字段加定时任务去硬缝。状态越缝越多，漏判、重判、并发冲突也就全找上门了。

既然痛点是这两个，那工作流引擎——或者大家常说的流程引擎、编排框架——到底是来干嘛的？说白了，就是把这些脏活累活接过去。不管各家框架叫什么名字，核心替你干的无非就三件活：

**第一件：调度。** 就像给流水线配了个认死理的调度员。你先把流程规则定好——可以画成直观的图，也可以写成规整的代码。调度员照着这份正本一步步推进，该分岔时按条件选路，该并道时等齐了再走。系统从此有了一本明白账，谁来问订单要过哪几关，把这份正本翻开给他看就行。

**第二件：记忆。** 订单停下来等人的时候，引擎替你把案发现场完整保存下来——“当前走到第几步了、手上拿着哪些数据”，规规矩矩存进数据库（也就是持久化）。哪怕订单要等上三天，中间服务器因为发版重启了五回，等买家付款的消息一到，引擎直接读档唤醒，从原地接着往下跑。再也不用你去满大街写定时任务扫表了。

**第三件：兜底。** 流程跑在真实的系统环境里，磕磕碰碰是常态。调库存接口超时了，引擎能按策略自动重试；等用户付款等超了 30 分钟，引擎自动触发超时分支；要是走到一半发现走不通要退回，引擎还能按顺序执行反向动作，比如退款、释放库存——在业务流程里，这种回滚操作通常叫“补偿”。这些异常分支手写起来最容易漏，交给引擎就有了一套标准章程。

理清了这三件活，再回头看咱们那张订单，你会发现一个特别有意思的节奏：

下单那一刻的检查，几十毫秒内连贯执行完，主要用得上“调度”；而后面那一大串动辄等上几小时、几天的付款和发货，调度、记忆、兜底全都要派上用场。这也引出了工作流领域的两大阵营。

## 两种截然不同的流程，两类各显神通的工具

### 一口气跑完的：流程编排

先看下单那一瞬间。校验用户身份、查库存、算满减、过风控，全程跑在内存里，一眨眼功夫就完事，中途根本不需要停下来等外部事件，自然也不用把进度存进数据库。

这类场景要的就是轻、快，业内一般叫**流程编排**或规则引擎。国内常见的有 LiteFlow 和阿里的 compileflow。

它们的核心思路，是把原本挤成一团的业务逻辑拆成一个个独立的小卡片（组件），再用一张图或者一份规则配置把卡片串起来。哪天运营说“风控检查要挪到算满减前面”，你改改配置或者拖拖连线就行，用不着去动底层主干代码。

不过喝茶聊天说句掏心窝的话：**这类一口气跑完的流程，很多时候根本没必要引入专门框架。** 如果逻辑一共就那么四五步，一年半载也不怎么改，老老实实把大方法拆成几个命名清楚的小方法，分支复杂了顺手套个策略模式，代码就已经足够干净好读了。只有当业务步骤特别多、各种组合变体极其繁琐，或者三天两头需要不改代码调整顺序时，编排框架的价值才体现得出来。

### 会停下来等的：长流程

等买家付款、等仓库发货、等物流签收、等七天结算，这后半段才是工作流引擎真正的大本营。

这类流程最大的特点就是会“停下来等”，而且一等就是几天。这时候必须依赖持久化能力，保证系统重启后进度不丢。在这个阵营里，江湖上主要分成了两派：

**画图派：BPMN 引擎。** BPMN（业务流程模型与标注）是一套描述业务流程的国际标准画法。在这套标准里，圆圈代表事件、方框代表任务，菱形代表分岔路口（术语叫“网关”），此外还有专门画定时器和人工审批的图标。你画好流程图，引擎在后台读取这份定义，边解释边执行，每走一步就把当前进度存进数据库。

这一派的招牌选手是 Activiti，以及后来从 Activiti 分出来的 Flowable 和 Camunda。画图派最大的优势，在于流程图天然就是技术和业务之间的“通用语言”。产品经理、业务人员能看懂，甚至能一起对着画布推演逻辑。所以在 OA 审批、银行贷款审批、保险理赔这种“流程本身就是业务核心”的领域里，BPMN 引擎特别常见。

**代码派：持久化执行。** 但很多后端工程师并不喜欢画图。在他们看来，图形拖拽出来的流程文件在做代码评审时很难看清改动差异（diff），写单元测试也不顺手，不如让流程直接就是一段干净利落的普通代码。

这一派的代表是 Temporal，它脱胎于 Uber 内部的 Cadence。在 Temporal 里，“等用户付款，最多 30 分钟”就是一行极其朴素的代码。表面上看就像让程序睡了半小时，但底层完全不占任何线程资源，机器中途重启也丝毫不影响。Netflix 开源的 Conductor 也属于类似的编排思路，它用 JSON 描述流程，主要用来编排微服务。

两派各有所长，没有高下之分：如果流程需要经常跟业务方坐在一起讨论确认，选画图派；如果流程主要由研发维护、需要跟系统代码深度咬合，代码派会舒服得多。

### 还有第三条路：状态机

有时候你并不需要一个大而全的引擎来统管全局。状态机走的是另一套哲学：它压根不操心“下一步接着干什么”，它只认死理地管好“状态跳转的规矩”。

比如对于订单，它严格规定：只有在“待付款”状态下收到“支付成功”事件，才能跳到“待发货”；如果在“待付款”收到“超时事件”，只能跳到“已取消”；处于其他状态时收到莫名其妙的事件，统统拒绝。

很多团队靠着“数据库状态字段 + 状态机校验 + 消息队列”，就清清爽爽地管好了复杂的电商订单，根本没上任何工作流引擎。它虽然不替你做长流程的自动推进和状态记忆，但胜在结构清晰、极其透明。

## 掀开引擎的底盖：三种截然不同的原理

同样叫流程引擎，各家肚子里的齿轮到底是怎么咬合的？了解底层原理，排查诡异问题时心里才会有底。市面上的工具大致可以归纳为三种思路：

**编译成代码。** 这是阿里 compileflow 编译模式最鲜明的特色。你在画布上拖拖拽拽画了一张流程图，它在加载流程时把整张图翻译成原生的 Java 代码，再编译运行。掀开它生成的代码看，里面其实还是密密麻麻的 if-else，只不过不需要你手写了。好处是省掉了每一步解读流程定义的开销，跑起来很轻快；代价是流程定义一变就得重新生成，而且编译出来的代码本身只管一口气跑完，想中途停下来等几天，得另外靠持久化模块帮忙。

**解释执行加存状态。** 主流的 BPMN 引擎（如 Flowable、Camunda）基本都走这条路。引擎不把图编译成代码，而是读取流程定义文件，像个严谨的执行官一样，看着图纸一步步往前走。每迈过一个节点，就老老实实往数据库里写几条记录：“这个流程走到哪了、当前变量值是什么”。一旦遇到需要等人的环节，引擎就把线程释放掉；等下次外部事件来了（比如买家付完款的回调），引擎再去查数据库把状态捞出来，接着往下解释。它的好处是天然支持长等待，代价是每一步都有数据库读写开销。

**事件历史加代码重放。** Temporal 的设计最为巧妙。它既不存“当前停在哪张表的哪一行”，也不把图编译成代码，而是给每个流程实例配了一个记事本。流程运行过程中发生过的每一件事（调用了哪个接口、拿到什么结果、计时器什么时候到期）全部按顺序记成一份事件历史。

要是正在等付款的这 30 分钟里，机器突然故障宕机了怎么办？换一台新机器，把你的流程代码从头跑一遍。你可能会担心：那调过的接口岂不是要被重复调用一次？并不会。当代码跑到之前执行过的步骤时，Temporal 会去翻记事本：“这个接口在历史里已经调过了，当时返回的是 SUCCESS”，直接把历史结果塞回给代码，不再发起真实的网络请求。代码以极快的速度把旧逻辑一路“快进”过去，直到精准停在宕机前的位置，继续往下走。

不过这种机制带来了一条铁律：**流程主干代码必须是绝对确定性的。** 面对一模一样的历史事件，你的代码两次跑出来的路径必须严丝合缝一致。因此在 Temporal 的流程代码里，不能直接读系统当前时间、不能直接生成随机数，也不能直接发起网络请求。取时间、取随机数要改用 SDK 提供的确定性版本（比如 `Workflow.currentTimeMillis()`），调接口这类有副作用的事则拆成独立的 Activity（活动），交给引擎去调度和记录。

## 别光看贼吃肉：引入引擎的代价

聊到这儿，可能有人摩拳擦掌，恨不得明天上班就给项目里所有的业务都套上工作流。先刹刹车。软件工程里没有免费的午餐，工作流引擎消灭了业务逻辑里的混乱，但也带来了它自己的代价：

第一，**凭空多了一套基础设施要伺候。** 内嵌 Flowable、Activiti 这类 BPMN 引擎，数据库里会多出几十张引擎自己的表，历史数据日积月累，得定期清理归档；上 Temporal 或 Camunda 8，则要单独部署一套服务集群和存储。运维、监控、告警、备份，哪一样都得花人力照看。

第二，**排查问题的链路变长了。** 以前代码抛了个空指针，打开日志看一眼调用栈，第几行报错一目了然。上了引擎之后，控制台一报错，翻开堆栈全是一长串引擎内部的调度类和拦截器，真实的业务代码早被层层包裹住了。你得学会用引擎自带的工具或界面，去查“这个流程实例究竟走过哪些步骤”。

第三，**流程改版是个货真价实的深坑。** 代码改个规则直接上线就行，但长流程不一样。假设你把订单“付款等待时间”从 30 分钟改成 15 分钟，新代码发布上线的那一刻，数据库里可还躺着几千个昨天创建、正在等付款的旧订单呢！这些在途的旧实例到底该继续按老规矩等 30 分钟，还是迁移到新版本？成熟引擎虽然有版本管理机制，但怎么平稳过渡，需要你在设计时提前想好对策。

第四，**团队必须消化新的学习成本。** BPMN 规范里各种网关、事件、任务有几十种符号，画规范并不容易；而用 Temporal，全组人都得死死记住确定性约束的条条框框，一不小心在流程主干里随手取了个当前时间，重放时就可能走出不一样的路，引擎报出非确定性错误，流程卡在原地。

## 什么时候该用？灵魂三问与选型建议

下次再看到项目里分支逻辑横飞，别急着把引入引擎当成灵丹妙药。动手之前，不妨先问自己三个问题：

1. **流程中途需要停下来等吗？** 等人审批、等外部回调、等时间到期。如果自始至终是一口气跑完的，你需要的最多是一个轻量编排，很可能连框架都不用。
2. **流程需要经常拉着不写代码的人一起看吗？** 如果产品经理、运营甚至业务专家需要经常对照着流程图推敲规则，BPMN 那一派的可视化图纸非常有价值；如果从头到尾只有工程师自己在维护，代码派往往更顺手。
3. **流程变得勤吗、业务复杂吗？** 如果流程就三五个步骤、一年半载改不了一回，状态字段加状态机已经足够好用，硬上引擎反而得不偿失。

理清这三点，大致的选型路线其实非常清晰：

- 一口气跑完的简单流程：写好代码，大方法拆小，善用策略模式。
- 一口气跑完，但步骤特别多、分支组合繁琐：考虑 LiteFlow 这类轻量编排框架。
- 需要停下来等，并且流程图要给业务方看：看 Flowable 或 Camunda。
- 需要停下来等，主要由工程师以代码为主导掌控：看 Temporal。

工作流引擎不会凭空让复杂的业务变简单。它真正能替你做到的，是把原本东躲西藏、散落在代码和定时任务缝隙里的流程拎到台面上来。让混乱的逻辑有一份看得见的正本，让漫长的等待有靠谱的管家替你记账。

先想清楚你的订单到底需不需要“停下来等”，再去挑最趁手的工具。

### 代码派长什么样

下面是“等用户付款，最多 30 分钟”在 Temporal Java SDK 里的大致写法（示意，省略了接口声明和配置）：

```java
public class OrderWorkflowImpl implements OrderWorkflow {
    private boolean paid = false;

    @Override
    public void run(Order order) {
        activities.reserveStock(order);              // 普通步骤，失败会按策略自动重试
        boolean ok = Workflow.await(Duration.ofMinutes(30), () -> paid);
        if (!ok) {                                   // 30 分钟内没等到付款
            activities.releaseStock(order);
            return;
        }
        activities.notifyWarehouse(order);
    }

    @Override
    public void paymentReceived() {                  // 支付回调通过 Signal 送进来
        paid = true;
    }
}
```

那 30 分钟里，没有任何线程在空等；服务器重启后，Temporal 会通过重放把流程恢复到 `await` 这一行继续等。

### 延伸阅读

- **BPMN 2.0.2 规范**：[omg.org/spec/BPMN/2.0.2](https://www.omg.org/spec/BPMN/2.0.2/)。不用通读，先认识开始事件、任务、排他网关、并行网关、定时器事件、用户任务这几种元素，看任何 BPMN 流程图都会顺很多。
- **Temporal 文档**：[docs.temporal.io](https://docs.temporal.io/)。先读 Workflow、Activity、Signal 的概念介绍，重点理解为什么流程代码必须是确定性的。
- **Camunda 文档**：[docs.camunda.io](https://docs.camunda.io/)。即使不用 Camunda，它对 BPMN 各元素的讲解和建模最佳实践也很好读。
- **Flowable 文档**：[flowable.com/open-source/docs](https://www.flowable.com/open-source/docs/)。想在 Spring Boot 里内嵌一个开源 BPMN 引擎，从这里开始。
- **书**：Bernd Rücker《Practical Process Automation》（O'Reilly，2021）。作者是 Camunda 联合创始人，书里系统讨论了编排与事件驱动协作的取舍、长流程的设计，比单看某个框架的文档视野更宽。
- **原视频**：[BV13d4y1o7iB](https://www.bilibili.com/video/BV13d4y1o7iB/)，5 分钟的 compileflow 可视化设计器实操，界面是 2022 年的旧版插件，可以当作“流程编排长什么样”的直观演示。
